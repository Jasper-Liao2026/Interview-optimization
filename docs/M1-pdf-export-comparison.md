# M1-6 · 简历 PDF 导出三方案对比

> 结论先行：**主路径选 B（服务端无头 Chromium 打印），C（浏览器原生打印）作为前端零依赖的备用入口，A（前端 `@react-pdf/renderer`）否决。**
> 判据不是「哪个能出 PDF」——三个都能出。判据是 **「导出结果与屏幕预览是否结构上一致」**，因为简历是给人看的东西，预览与导出一旦有偏差，用户就要靠肉眼在一页纸里找茬，而我们没有能力保证每一次改动都人工比对一次。

本文的每一个数字都来自本仓库的实测产物（`scripts/_m1_out/`），复现命令见文末 §7。

---

## 1. 三方案是什么

| 代号 | 做法 | 渲染内核 | 代码位置 |
|---|---|---|---|
| **A** | 前端用 `@react-pdf/renderer` 把简历数据重新排一遍版，产出 PDF 字节 | 自有的 Yoga 排版引擎（**与浏览器无关**） | 实验环境 `scripts/pdfproto/render.mjs`（与产品依赖隔离） |
| **B** | 服务端把**预览用的那份 HTML** 交给无头 Chromium 打印 | Blink（**与用户浏览器同一个**） | `apps/api/app/pdf/export.py` |
| **C** | 浏览器把同一份 HTML 载入为顶层文档，调 `window.print()`，用户在打印对话框里存 PDF | Blink（同上） | `apps/web/src/app/print/[id]/page.tsx` |

关键差异不在「谁的 PDF 更好看」，而在**同一份简历数据要被表达几次**：

- A：**两次**。一次在 HTML 模板里（给屏幕看），一次在 React-PDF 的 StyleSheet 里（给纸看）。两份代码没有共享，改一处必须记得改另一处。
- B / C：**一次**。`apps/api/app/render/templates/resume_classic.html.j2` 既是预览的来源，也是 PDF 的来源。

## 2. 四维对比

| 维度 | A · React-PDF | B · 服务端 Chromium | C · 浏览器原生打印 |
|---|---|---|---|
| **① 与预览的一致性** | **低**。两套布局代码，一致性靠人自觉维持。实测内容完整（19/19 要点）但**分页分布与 B 完全不同**（见 §4.2） | **结构性一致**。打印的就是预览那份 HTML，不可能不一致 | **与 B 等价**。同一份 HTML、同一个引擎；实测内容字符数与 B 只差 3 字（见 §4.3） |
| **② 基础设施成本** | 前端多一棵依赖树：实测 **48 个顶层包 / 2154 个文件 / 29.6 MB**；且必须自带中文字体文件 | **零新依赖**。直接调用本机已装的 Chrome / Edge（`find_chromium()` 自动探测），不下载 Playwright 内核 | **零依赖**。浏览器自带能力 |
| **③ 谁决定产物** | 代码决定。服务端/前端都能算，适合批量 | 服务端决定。可批量、可无 UI、可直接 `BytesIO` 返回 | **用户决定**。打印对话框里的边距、页眉页脚、纸张都由用户在那一刻选，我们只能给建议 |
| **④ 失败模式** | 中文断行要自己补（§3.1）；分页由自研算法决定，调优成本高 | 需要机器上有浏览器；需要管超时、临时目录、进程残留（全部收在 `export.py`） | 依赖用户手动操作；默认会加上页眉页脚（§4.3）；无法在 CI 里自动验收 |

## 3. 方案 A 暴露的两件事（给「不用 A」提供了硬证据）

### 3.1 react-pdf 不内置中文断行 —— 中文长句会**直接冲出纸面**

第一版移植（字号、行高、边距全部按 CSS 那份照抄）产出后，用 PyMuPDF 量文字边界：

```
sample_A_react_pdf.pdf:  页宽 595.3pt  右边距上限 549.9pt  实测最右 599.0pt  溢出 +49.0pt  越界 2 处
sample_B_server_chromium.pdf: 页宽 595.0pt  上限 549.6pt  实测最右 549.7pt  溢出 +0.1pt  越界 0 处
```

`599.0 > 595.3` 意味着**文字已经跑出纸张外**。根因：react-pdf 的换行器按**空格**切词，而中文没有空格，整段中文被当成一个不可断的「词」，放不下就直接溢出。

修法是注册断行回调，把含中文的「词」逐字拆开：

```js
Font.registerHyphenationCallback((word) => {
  if (!/[\u2E80-\u9FFF\u3000-\u303F\uFF00-\uFFEF]/.test(word)) return [word];
  return Array.from(word).flatMap((char) => [char, ""]); // 后随空串，避免插入连字符
});
```

修后溢出从 **+49.0pt 降到 +2.2pt**（1 处，来自 Latin 词 `trace_id` 未被拆分），已可交付，但**没有归零**。

> 这一课在 HTML/CSS 那边根本不存在 —— 浏览器自带 CJK 断行。换一个排版引擎，就要把「中文怎么断行」重新学一遍。这正是「第二套布局代码」的真实代价：不只是多写一遍样式，而是**多踩一遍渲染引擎的坑**。

### 3.2 条目不跨页与「把纸填满」在 A 里互相打架

两边都表达了「一段经历不要被分页拆开」：CSS 用 `break-inside: avoid-page`，react-pdf 用 `wrap: false`。结果：

| | 第 1 页承载的经历 | 第 1 页字符数 | 第 2 页字符数 |
|---|---|---|---|
| **A** | 1 段（实习经历） | 514 | 1316 |
| **B** | 3 段（实习 + 两个项目） | 1426 | 385 |

**A 的第 1 页只用掉三成**：它把「项目经历」这一整个分区推到了第 2 页，于是留出大片空白；而 B 靠浏览器的分页算法，在同样的「不许拆条目」约束下把 3 段经历排进了第 1 页。

B 能做到这一点不是巧合 —— Blink 的分页是「逐块尝试、放不下才推」，而 react-pdf 的 `wrap: false` 语义更粗：整段放不下就整体下沉，且会连带影响其所在分区的其余内容。要把它调到与浏览器同级，只能针对每份模板反复试参数。

对简历这种**一页纸决定印象**的东西，「第 1 页空掉大半、内容全挤在第 2 页」是实打实的体验损失。

## 4. 三份样例的实测对照

### 4.1 输入（三份完全共用）

来自 `scripts/m1_make_samples.py` → `resume_sample.json` / `sample_input.html`：

- 3 个分区、4 段经历、19 条要点
- 模板渲染出的 HTML 6,386 字符
- 内容长度刻意做成**必然跨页**（否则「分页是否正常」这个对比不成立）

### 4.2 探针结果（PyMuPDF 逐页抽取）

| 指标 | A · React-PDF | B · 服务端 Chromium | C · 浏览器打印 |
|---|---|---|---|
| 文件大小 | 90,162 B | 161,945 B | 210,556 B |
| 页数 | 2 | 2 | 2 |
| 第 1 页字符数 | **514** | 1426 | 1525 |
| 第 2 页字符数 | 1316 | 385 | 484 |
| 嵌入字体 | DengXian / DengXian-Bold（我们自带并注册的） | Microsoft YaHei 3 个子集（浏览器按 CSS 字体栈自己选的） | MS YaHei + Arial（Arial 来自页眉页脚） |
| 中文可抽取 | 是（首页含 CJK） | 是 | 是 |
| 内容右边界 vs 上限 | **+2.2pt**（1 处越界） | **+0.1pt**（0 处） | +21.7pt（**1 处，是浏览器页脚 URL，非正文**） |
| 内容完整性 | 19/19 要点齐全 | 19/19 | 19/19 |

三份的**内容都完整、中文都正常嵌入**（可抽取 = 字体带 ToUnicode 映射，不是画成图形）。差异集中在**「怎么排」**。

### 4.3 C 与 B 的差异只有「谁加的页眉页脚」——这恰好可量化

C 每页比 B 多 **99 个字符**，且两页的增量一致。逐项对上：

- 页眉：日期 `2026/10/9 19:18`（15 字）+ 标题 `本地开发用户 · 后端开发工程师（校招）`（20 字）
- 页脚：页面 URL（58 字）+ 页码 `1/2`（3 字）

15 + 20 + 58 + 3 = 96 ≈ 99。**扣掉页眉页脚，C 的正文是 1525 − 96 = 1429 字，B 是 1426 字，差 3 字。**

> 也就是说：C 与 B 的正文排版**等价**（同一个 Blink、同一份 HTML），差别只在 C 由用户手动触发、于是被塞进了浏览器默认的页眉页脚。
> 页脚 URL 正是那次「+21.7pt 越界」的唯一来源 —— **问题不在我们的内容，而在打印对话框的默认勾选**。用户取消勾选「页眉和页脚」即可消除。

结论落回 §2 的维度③：**C 的产物由用户决定**——这是它的特点，也是它不能作为批量直出主路径的原因（M7-5 的批量场景需要一个确定性的服务端产物）。

## 5. 方案 C 当初为什么打出一页空白（以及怎么修的）

最初实现是把服务端 HTML 塞进 `srcDoc` iframe，再 `window.print()` 打印外层页面。实测产出 **3 页，第 1 页 0 字符**。两层原因叠加：

1. **iframe 文档里的 `@page` 不作用于外层的打印任务** —— `@page` 只对「被打印的那个文档」生效，而这里被打印的是父文档；
2. 模板在 `@media print` 下又把 `.page` 的内边距清成了 0（因为它假设边距由 `@page` 提供）。

两者一叠加：正文贴着纸边，外层再补一层 padding 去「救」，结果溢出并产生空白页。

修法不是继续加 padding 打补丁，而是**换掉承载体**：把简历 HTML 用 `document.write` 写成**顶层文档**，那么它自带的 `@page` 与 `@media print` 就都作用在正确的文档上。

修后：3 页 → **2 页**，第 1 页 0 字符 → 1525 字符，且与 B 的正文排版一致（§4.3）。

> 代价：这一页的 React 树会被 `document.write` 抹掉。对一个「只用于自动打印、不需要再交互」的路由，这是可接受的交换；屏幕上需要持续交互的预览在 `/generate` 页里，用的仍是 iframe。
> 结论是可复用的经验：**同一份 HTML 要用于「打印」时，让它当顶层文档；要用于「预览」时，才放进 iframe。**

## 6. 决策

**主路径 B，备用入口 C，否决 A。** 理由按权重排序：

1. **一致性是结构保证的，不是流程保证的。** B/C 打印的就是预览那份 HTML；A 需要两套代码长期对齐，而我们没有足够的回归手段去保证「改了模板没改 StyleSheet」。
2. **A 的坑要一个个填，且填不到零。** 中文断行要自己注册回调（§3.1），分页填充率要靠试参数（§3.2）。而 B/C 这些问题由浏览器解决。
3. **B 在成本上并不贵。** 零新依赖，直接复用本机浏览器；代价是进程管理，而这块是一次性的，已收敛在 `export.py` 一个文件内。
4. **批量场景只能走 B。** 素材库 → 批量出简历（M7-5）时没有「用户点一下」这个动作，C 排除在外。

A 并非一无是处：它是**唯一**不依赖浏览器进程、能在纯 Node 环境里跑出 PDF 的方案，如果将来某天必须部署到没有浏览器的运行时，它是备选。因此本仓库把它的排版代码留在 `scripts/pdfproto/` 里作为**实验记录**（该目录自带 `package.json`，与 `apps/web` 的依赖完全隔离，不进产品构建），而不是删掉了事——**否决一个方案时要留下它的证据**。

## 8. 面试可讲点

- **判据选对了，方案就不用争。** 三个方案都能出 PDF；把判据从「能不能出」换成「导出与预览的一致性是不是结构保证」，A 就自然出局——不需要比较谁的字更好看。
- **「同一个引擎」可以量化验证，而不是嘴上说说。** C 比 B 每页多 99 字，逐项对下来正好是页眉（日期+标题）+ 页脚（URL+页码）；扣掉后正文差 3 字。这比「它们都是 Chromium 所以应该一样」有力得多。
- **跨引擎的真实成本不是「多写一遍样式」，而是「多踩一遍坑」。** react-pdf 不内置 CJK 断行，中文长句会跑出纸张（实测 599.0pt > 595.3pt 页宽）；这个坑在浏览器侧根本不存在。
- **修 bug 时先判断「该补哪一层」。** C 的空白首页，加 padding 是在错误的一层打补丁；把 HTML 提升为顶层文档才是让 `@page` 作用到正确对象上。
- **否决方案要留证据。** 方案 A 的实验环境与其「中文溢出 49pt / 第 1 页只用三成」的实测数据都留在仓库里，而不是删掉后只留一句「A 不好」。
