## 1. 这一版解决了什么

M1 结束时，素材库只有 curl 能写：`POST /api/v1/experiences` 是唯一入口，前端只有一个能勾选的只读列表。
M2 把它补成了**用户能真正维护的经历库**：

| 能力 | M1 结束时的状态 | M2 之后 |
|---|---|---|
| 录入 | 只能 curl / 脚本 | `/library` 表单，新增 / 编辑 / 删除 |
| 浏览 | 生成页里的扁平勾选列表 | 按实习 / 项目 / 校园分组，组内按经历时间倒序 |
| 量化结果 | 和定性要点混在一个 `text[]` 里 | 独立 `metrics`，三要素（指标名 / 数值 / 口径） |
| 同一条目的多种写法 | 无处安放 | `variants`，按岗位方向存多份表述 |
| 编辑 | 不支持 | `PUT /experiences/{id}`，全量替换语义 |

**M2 的核心不是「加了一个页面」**，而是让 M4-7「改写不得编造数字」这条产品红线第一次有了结构支撑——
见下面第 3 节。

## 2. 数据模型变更

migration：`supabase/migrations/20261010000000_m2_library.sql`（**只加列，不改不删**）

```
public.experiences
  + metrics  jsonb  not null default '[]'   -- [{name, value, context}]
  + variants jsonb  not null default '[]'   -- [{direction, text, note}]
  + idx_experiences_user_kind_time          -- (user_id, kind, end_date desc nulls first, start_date desc nulls last)
```

两条设计取舍：

**`metrics` 用 jsonb 而不是子表**，与 `job_descriptions.parsed` 保持同一取舍：
形状还在演化、只在条目内读写、不做跨条目聚合。代价是失去列级约束，由 Pydantic 在写入前兜住。

**`variants` 用条目行内的 jsonb 而不是 1:N 子表**：变体是**派生内容**（事实源仍是 `raw_description`），
M2 阶段只做「存下来 + 展示」，不参与跨条目检索，因此列表页免 join、写入在一个事务内完成。
若 M5 真要「按变体打分 / 按方向检索」，那时再迁到 `experience_variants` 子表，成本就是一次数据搬运。

**`sort_order` 语义降级**：M2 起列表不再让用户手工排序（按经历时间倒序），该列**刻意保留**——
删列要动 M1 的 seed 与仓储，而 M6/M7 若要「手动指定简历里经历的先后」可以原地启用。
列上写了 comment 说明这件事。

## 3. 关键设计：量化结果为什么要拆出来

M4-7 的红线是「改写内容必须可回溯到原始条目，不得编造」。数字是最容易被编造、也最难事后发现的东西。

拆之前，「量化要点」和定性描述混在同一个 `text[]` 里：

```
highlights = ["负责订单查询接口的重构", "P99 从 800ms 降到 120ms", "参与线上问题排查"]
```

事后只能做**字符串比对**——而改写会把整句话重述一遍，字面就对不上了，校验等于没有。

拆之后：

```json
metrics  = [{"name": "订单查询接口 P99 延迟", "value": "800ms → 120ms", "context": "压测 5000 QPS 下"}]
highlights = ["负责订单查询接口的重构"]
```

改写 prompt 里因此能写出一条可执行的规则（`agents/prompts.py`）：

> **凡写到数字，必须逐字来自「量化结果」区块。不得换算单位、不得四舍五入、
> 不得把「24 → 82 条」写成「增长 240%」。「量化结果」为空时，全文不许出现任何数字成果。**

对应的校验就变成：「改写文本里出现的每个数字，都能在 `metrics` 的 `value` 里找到子串」——
可自动化、可写测试。这是 M2 里唯一一处「多花了建模成本、但换到了下游确定性」的地方，值。

⚠️ `value` **刻意保持字符串**，不解析成数字 + 单位。简历里的量化写法千奇百怪
（`24 → 82 条`、`3000+`、`下降 40%`），强行结构化只会让用户在录入表单前跟格式较劲。
子串匹配不需要理解数值语义。

## 4. 接口变更

| 端点 | 变化 |
|---|---|
| `GET /api/v1/experiences` | 排序改为**按 kind 分组 → 组内经历时间倒序**（进行中 `end_date is null` 排最前）；返回新增 `metrics` / `variants` |
| `POST /api/v1/experiences` | 接受 `metrics` / `variants`（均可省略，默认 `[]`） |
| `PUT /api/v1/experiences/{id}` | **新增**。全量替换语义 |
| `DELETE /api/v1/experiences/{id}` | 不变 |

**为什么是 PUT 而不是 PATCH**：编辑表单提交的就是整条记录，全量语义下「必填字段缺失」
由 Pydantic 直接拦成 422，不需要在服务层区分「字段没传」和「显式置空」这两种 PATCH 特有的歧义。
代价是调用方必须知道「不传 = 清空」，这一点写进了接口 description，并有测试锁住
（`test_put_is_full_replace_not_merge`）。

新增的三条**接口层校验**（都在 Pydantic，都在提交时报 422 而不是等到数据库抛 500）：

1. `variants` 同方向重复 → 422。同一条经历同一方向只允许一份表述，这是「哪个版本生效」不该有歧义。
2. `end_date < start_date` → 422。migration 里有同名 check 约束，**刻意重复一遍**：
   数据库抛的 `CheckViolation` 到接口层会变成 500，而用户填错日期是用户侧问题。
3. 子结构字段长度上限，防止把整段文本塞进「指标名」。

## 5. 前端

新增 `apps/web/src/app/library/page.tsx`（客户端组件，约 500 行）：

- **列表**：按 实习 → 项目 → 校园 三组渲染。分组顺序由前端固定，
  因为后端返回的顺序是 `kind` 的字典序（campus / internship / project），与展示顺序不同——
  **排序只有一个说法**：后端负责组内次序，前端只负责分到哪一组。
- **表单**：新增 / 编辑共用一套；`metrics`、`variants`、`skill_tags`、`highlights` 都是可增删的行或按行输入的 textarea。
- 提交时把**全部**字段发出（PUT 全量语义）；`sort_order` 显式传 `0`
  —— 类型管线对「带 default 的字面量字段」会生成必填，这是 M1 记录在案的契约现象，
  照做而不是在前端加 `?? 0` 兜底去掩盖它。

## 7. 踩坑记录

**1）验收脚本报 8 条失败，其中 PUT 返回 405 —— 是进程陈旧，不是代码有问题。**
本机 8000 端口上跑着 M1 时期留下的 uvicorn（已存活 2 小时）。新起的进程绑定失败但**没有报错**，
于是所有请求都由旧进程应答：PUT 未注册（405）、POST 响应里没有 `metrics`（旧 schema 直接忽略未知字段）。
教训：`Start-Process` 起服务后必须**验证新进程真的接管了端口**（探 `/openapi.json` 看新端点是否在），
而不是只看进程起没起。

**2）把 M1 验收里「schema 版本 == m1_0001」改成「≥ m1」才合理。**
M2 的 migration 会把 `service_meta.schema_version` 推到 `m2_0001`，锁死版本号的 M1 校验就会假失败。
M1 真正要证明的是「migration 流程跑得通」，不是「库永远停在 m1_0001」。
改成解析里程碑编号后比较，后续每个里程碑都不必再回来改这条。

**3）seed 在 migration 之后执行，所以 seed 里的版本标记必须跟着 migration 一起推进。**
否则「首次初始化」会先把版本升到 m2、再被 seed 覆写回 m1，让 `/system/info` 读到一个骗人的版本号。

**4）验收脚本里「同 kind 必须连续」的断言一开始写错了。**
写成了「相邻两条 kind 必须相同」——那只在所有条目同 kind 时才成立。
正确判法是「新块起始的个数 == 不同 kind 的个数」。断言写错会让人去查业务代码，
这是自己给自找的排查成本。

## 8. 面试可讲点

**「量化结果」的建模动机**：不是「字段更整齐」，而是把一条**产品红线**从「靠 prompt 请求模型别乱写」
变成「有参照集合可以自动校验」。同一件事在 M4-7 会变成一条真正跑起来的校验规则。

**jsonb vs 子表的取舍说得出代价**：选 jsonb 是因为变体在 M2 不参与跨条目检索；
同时明确说出「什么时候该反悔」——M5 要按变体打分时迁移，成本是一次数据搬运。
设计决策的价值在于知道失效条件，不在于选对了。

**PUT vs PATCH 的取舍挂在类型系统上**：全量语义让「必填字段缺失」由 Pydantic 拦成 422，
省掉 PATCH 的「字段没传 vs 显式置空」歧义；代价（不传即清空）写进文档并有测试锁死，
而不是留成口头约定。

**验收脚本的设计原则**：能自动判定的就自动判定；缺服务标 SKIP 而不是报 FAIL；
造出来的测试数据自清理。这三点合起来是「这个脚本可以随便跑，不会骗你也不会污染你的数据」。
